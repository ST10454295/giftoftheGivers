# Final POE completion and evidence checklist

The archive contains implementation and reproducible configurations, but this checklist distinguishes those artifacts from account-specific evidence that must be generated by the team. Do not submit planned steps as completed evidence.

## 1. Personalise and open the solution

1. Extract `GiftOfTheGivers_Final_POE.zip` to a short folder path, for example `C:\APPR\GiftOfTheGivers`.
2. Open `Giftofthe_Givers.sln` in Visual Studio 2022 with the .NET 9 SDK.
3. Restore NuGet packages. If restore fails, check internet access and Visual Studio's NuGet package sources.
4. Configure `ConnectionStrings__DefaultConnection` through Visual Studio User Secrets for local development. Never commit production credentials.
5. Apply your existing schema/migrations. Set up an account securely in the current PowerShell window, then run the account utility:

   ```powershell
   $secure = Read-Host "Database connection string" -AsSecureString
   $ptr = [Runtime.InteropServices.Marshal]::SecureStringToBSTR($secure)
   try { $env:ConnectionStrings__DefaultConnection = [Runtime.InteropServices.Marshal]::PtrToStringBSTR($ptr) } finally { [Runtime.InteropServices.Marshal]::ZeroFreeBSTR($ptr) }
   dotnet run --project AccountProvisioner
   ```

   Choose `Donor` or `Employee`; the password prompt is hidden. For an employee, choose whether to create a starter project. Then run the app and tests.
6. Review the user manual and team report; replace every instruction placeholder with verified screenshots/team evidence.

## 2. Unit and integration tests (Section A1/A2)

1. In Visual Studio Test Explorer, build and run all tests in `Giftofthe_Givers.Tests`.
2. Confirm all donation validation tests and the home-page integration test pass.
3. Save a screenshot of Test Explorer with the pass count and a screenshot of the test output. Export the `.trx` result if your lecturer accepts it.
4. The supplied test project also contains Selenium UI tests. Run these with Chrome installed and the application already running. Set `APP_BASE_URL` to the running URL if it is not `https://localhost:7167`.

## 3. Load/stress evidence (Section A3)

1. Install k6 on a machine that can reach the deployed app.
2. Start with `k6 run -e BASE_URL=https://YOUR-APP.azurewebsites.net -e VUS=20 -e DURATION=1m load-test/home-load.js`.
3. Save the terminal summary and the k6 dashboard/export graph. Record the date, target URL, virtual users, duration, request count, error rate, and p95 latency.
4. For a stress test, raise VUS gradually (for example 20, 50, then 100) and stop if the service becomes unhealthy. Do not load-test a production service without the organisation's approval.

## 4. Selenium UI evidence (Section A4)

1. Start the app and ensure database seed data exists for the selected flows.
2. Run the Selenium test project with Chrome.
3. Save passing test output and browser screenshots for both flows. Extend coverage with negative/invalid amount and invalid volunteer input if time permits.

## 5. GitHub Actions CI (Section B)

1. Push the finished solution to the team's GitHub repository and ensure the default branch is `main` (or edit the workflow branch list).
2. Open **Actions** and confirm the `build-test-deploy` workflow restores, builds, runs tests, and uploads the TRX artifact.
3. Save screenshots of the workflow file, a successful run, and the test result artifact.
4. A public push triggers the workflow. Do not commit secrets to YAML or source files.

## 6. Azure deployments (Section C)

1. Create/confirm an Azure App Service for the web app, an Azure Function App using the .NET isolated worker, and an Azure SQL database.
2. Set GitHub repository variable `AZURE_WEBAPP_NAME` and secret `AZURE_WEBAPP_PUBLISH_PROFILE`.
3. Set GitHub repository variable `AZURE_FUNCTIONAPP_NAME` and secret `AZURE_FUNCTIONAPP_PUBLISH_PROFILE`.
4. In App Service configuration, add `ConnectionStrings__DefaultConnection` with the Azure SQL connection string. Configure SQL firewall/network rules and TLS. Keep all secrets in Azure/GitHub secret stores.
5. Run the `main` branch workflow. Verify the web app URL loads and POST to `https://YOUR-FUNCTION.azurewebsites.net/api/generate-certificate` with valid JSON; verify an invalid body returns HTTP 400.
6. Save screenshots of App Service deployment status, Function App deployment status, the live site, and the successful/invalid function POST response. Do not publish access keys or connection strings in screenshots.
7. Configure `GiftOfTheGivers.Functions1` with `FUNCTIONS_WORKER_RUNTIME=dotnet-isolated` and `AzureWebJobsStorage` as required by your hosting plan.

The workflow deploys the function and web app, but SQL connection setup and SQL script execution are manual. See `Database/README.md` and run the additive script only after confirming the actual database schema.

## 7. SQL update evidence (Section C3)

1. Back up the Azure SQL database.
2. Confirm the `Donations.DonationDate` and `Volunteers.RegistrationDate` columns exist.
3. Execute `Database/001_reporting_indexes.sql` in Azure Data Studio or SQL Server Management Studio.
4. Verify the indexes in `sys.indexes` and save before/after screenshots or query output.
5. If rollback is required, run `Database/001_reporting_indexes_rollback.sql`.

## 8. Handover and team report (Section D)

1. Complete the team report with every member's actual name, ID, role, completed work, and evidence (commits, PRs, test runs, deployment activity, documentation).
2. Do not assign work to a member who did not do it. If one member completed a task, state that accurately.
3. Attach the completed user manual with screenshots of the actual application.
4. Include the solution/project archive and evidence list required by your lecturer.
5. Confirm all screenshots are readable, show no credentials/personal donor information, and are from the final tested version.
